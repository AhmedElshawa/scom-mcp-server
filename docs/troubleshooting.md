# Troubleshooting

This document helps an operator diagnose the SCOM MCP receiver, the collection worker and the setup tooling. It starts with five quick checks and the log locations, then maps the stable machine codes the code emits (`SETUP_*`, `SCOM_*`, `ENTRA_*`, ingestion, live, publisher and worker codes) to where they are emitted, the likely cause and the fix. Causes are stated only where the code establishes them; otherwise the row says "internal consistency check; capture the operational log and open an issue". This is an unsigned community release; nothing here is a certification or a statement of customer acceptance. Related documents: [mcp-server-spec.md](mcp-server-spec.md), [configuration-reference.md](configuration-reference.md), [operations.md](operations.md), [network-and-ports.md](network-and-ports.md), [entra-setup.md](entra-setup.md), [service-accounts.md](service-accounts.md), [install-cli.md](install-cli.md), [security.md](security.md), [limitations.md](limitations.md), [architecture.md](architecture.md), [sizing-and-scope.md](sizing-and-scope.md), [copilot-studio-integration.md](copilot-studio-integration.md).

## First five checks

| # | Check | How | What it tells you |
|---|---|---|---|
| 1 | Receiver is up | `GET https://<FQDN>/healthz` (anonymous). Expect HTTP 200 and `{"service":"ScomReadOnlyMcp","version":"1.0.0"}` | Site, TLS binding and app pool are working. It says nothing about data freshness; call `get_source_status` for that. |
| 2 | Configuration is valid | `dotnet ScomMcp.dll --validate-setup <server-dir> <worker.json>` | `SCOM_SETUP_CONFIGURATION_READY` (0), `SCOM_SETUP_SOURCE_EVIDENCE_REQUIRED` (2) or `SCOM_SETUP_CONFIGURATION_INVALID ErrorType=<T>` (1). Receiver and worker settings that disagree are caught here. |
| 3 | Worker task status | `Operations\DurableIndexedRefresh\Get-ScomWorkerTaskStatus.ps1` | Inspect `TaskState`, `RuntimeState`, `RuntimeConsistency`, `LastOutcome`, `FailureCode`, `LastFailureCode`, `RearmRequired`, `LastPublicationUtc`. `RearmRequired=true` or a prior `running` state blocks the next start until an explicit rearm (see [Worker runtime state](#worker-scheduler-and-runtime-state)). |
| 4 | Receiver and worker logs | Read `server.log` and `worker.log` (see [Where logs live](#where-logs-live)). Look for `IngestionAccepted`, `IngestionRejected`, `WorkerFailed`, `CollectionDeferred` and their `Code` values | Whether publications arrive and why they are rejected or deferred. |
| 5 | Network, DNS and certificates | From the worker host resolve `<FQDN>` and open `https://<FQDN>/healthz`; check NSG/firewall rules for the HTTPS port, and that the worker host can reach Entra (`login.microsoftonline.com`) and `<MGMT_SERVER>` | `PUBLISHER_HTTP_*`, `PUBLISHER_RETRY_EXHAUSTED` and `PUBLISHER_TOKEN_*` are usually name-resolution, firewall, TLS or clock problems. See [network-and-ports.md](network-and-ports.md). |

## Where logs live

| Item | Location and naming | Source |
|---|---|---|
| Receiver operational log | `OperationalLogging.Directory` in `appsettings.json` (shipped value `C:\ProgramData\SCOMMCP\Logs`): `server.log`, rotated to `server.log.1` … `server.log.<RetainedFiles-1>` | `OperationalLogging.cs` |
| Worker operational log | `operationalLogging.directory` in `worker.json`: `worker.log` with the same rotation | `OperationalLogging.cs` |
| Collector profile log | `profile.configuration.operationalLogging.directory`: `scom-collector-profile.jsonl`, `.1` … (collector budgets: file 1024–16777216 bytes, default 1048576; 1–20 files, default 5) | `ScomOperationalLogging.psm1` |
| Directory lease | `operational.lock` in each log directory (1-byte role lease: server or worker). A directory shared by server and worker is refused. | `OperationalLogging.cs` |
| Worker runtime state | `--runtime-state-dir`: `worker.status.json`, `worker.runtime.lock`, `worker.stop.request` | `WorkerRuntimeState.cs` |
| Worker console | stderr lines such as `SCOM_WORKER_FAILED Code=...` | `Program.cs` |
| Setup journals and receipts | Setup private directory (see [install-cli.md](install-cli.md)) | `Setup\*` |

Log format: JSON lines with `Utc`, `Component` (`server` or `worker`), `Level`, `Event`, and optional `Outcome`, `DurationMs`, `Code`, `Attempt`, `MaxAttempts`, `DelaySeconds`, `LineNumber`, `BytePositionInLine`. The log is an allowlist projection: no free text, exception messages or scopes, Information level and above. Only allowlisted `Code` values are written (`WORKER_*`, `COLLECTION_ATTEMPTS_EXHAUSTED`, `SOURCE_UNAVAILABLE`, `LIVE_*`, `INVALID_ARGUMENT`, `NOT_FOUND`, `PUBLISHER_*`, `PUBLISHER_HTTP_<100-599>`); other codes are dropped, so a missing code is not proof that none occurred. `RetainedFiles` counts the active file. Directories must exist before start (setup creates them); the runtime never creates them.

Event names: `WorkerStarted`, `WorkerPublished`, `WorkerCancelled`, `WorkerFailed`, `CollectionStopped`, `CollectionPublished`, `CollectionDeferred`, `LiveDeferred`, `LiveSourceUnavailable`, `LiveDeliveryDeferred`, `LiveAdmitted`, `LiveReceived`, `LiveRejected`, `LiveTransportRejected`, `LiveFailed`, `IngestionAccepted`, `IngestionRejected`, `IngestionDeadline`, `ReadModelFailed`, `ToolFailed`, `RequestFailed`, plus operational-state events `Started`, `Stopped`, `Failed`, `RequestCompleted`, `CollectionCompleted`, `Diagnostic`. Outcomes: `Succeeded`, `Deferred`, `Cancelled`, `Failed`. The worker console also prints `SCOM_WORKER_STARTED`, `SCOM_WORKER_PUBLISHED`, `SCOM_WORKER_CANCELLED`, `SCOM_WORKER_FAILED`, `SCOM_LIVE_DEFERRED`, `SCOM_COLLECTION_PUBLISHED`, `SCOM_COLLECTION_DEFERRED`, `SCOM_COLLECTION_STOPPED`; the receiver emits `SCOM_INGESTION_ACCEPTED` (event, UTC, trace id, bytes). Collector profile events: `profile.started`, `configuration.validated`, `source.connected`, `scan.completed`, `profile.failed`, `setup.started`, `setup.completed`, `setup.failed`.

## Reading a failure

1. Find the newest `Code` in `worker.log` or in the worker console output.
2. For ingestion rejections, the HTTP 409 body carries `reason`; the receiver log keeps only a few reasons (see [mcp-server-spec.md](mcp-server-spec.md#9-ingestion-contract-publisher-to-receiver)).
3. The collector script only writes the umbrella `SCOM_GENERIC_PROFILE_FAILED` to stderr; the specific `SCOM_*` code is thrown inside the child process and is hidden from the log. How to surface it on demand: Not determined from source (run the preflight script, `Test-SCOMPreflight.ps1`, and the setup flow, which report check names, and capture the collector profile log).

## After a server restart: agent says `READ_MODEL_EXPIRED`

**Symptom.** After the host running the worker was rebooted, the agent answers every question with `SOURCE_UNAVAILABLE` / `READ_MODEL_EXPIRED` and no data. The scheduled task looks `Ready`, but its last result is nonzero (for example `0x1`), and running it from Task Scheduler appears to do nothing.

**Root cause.** The worker marks `worker.status.json` as `state=running` while it works. If the host reboots (or the process is killed) without a cooperative stop, that status stays `running` with the process id from before the reboot. On the next start the worker sees a prior `running` state it cannot explain, refuses to start (the task exits within about a second, return code 1) and sets the gate `RearmRequired=true`. Automatic rearm is intentionally absent, so no new dataset is published; once the last one is older than `UnavailableMinutes` the receiver reports `READ_MODEL_EXPIRED`. The data path (receiver, Entra, certificates, SCOM) is not at fault. The code `UNEXPECTED_PRIOR_RUNNING_STATE` identifies this case.

**Confirm.** On the worker host, in an elevated PowerShell:

```powershell
cd <package>\Operations\DurableIndexedRefresh
.\Get-ScomWorkerTaskStatus.ps1 | Format-List TaskState,LastTaskResult,RuntimeState,RuntimeConsistency,LastOutcome,LastPublicationUtc,RearmRequired,LastFailureCode
Get-CimInstance Win32_Process | Where-Object CommandLine -match '--worker'
```

The gated case shows `RearmRequired=True` (often `RuntimeConsistency=unknown-outcome-inspect-required`), `LastFailureCode=UNEXPECTED_PRIOR_RUNNING_STATE`, a `LastPublicationUtc` older than the reboot, and no worker process.

**Fix** (only when no worker process is running):

```powershell
.\Rearm-ScomWorkerTask.ps1 -AcknowledgeFailure -Confirm:$false
.\Start-ScomWorkerTask.ps1 -Confirm:$false
Start-Sleep 60
.\Get-ScomWorkerTaskStatus.ps1 | Format-List TaskState,RuntimeState,LastOutcome,LastPublicationUtc,RearmRequired
```

Expected: `TaskState=Running`, `RuntimeState=running`, `LastOutcome=published`, a new `LastPublicationUtc` and `RearmRequired=False`. `LastFailureCode` keeps showing `UNEXPECTED_PRIOR_RUNNING_STATE` as retained history; it no longer gates. Then ask the agent again (for example "Give me the inventory summary") and confirm with `get_source_status`, because task liveness is not data freshness.

**Do not**

- delete or edit `worker.status.json`, the checkpoint or other state files to "clear" the problem;
- run the worker as `SYSTEM` or any account other than the registered worker account (use the task, not a manual launch);
- run `Rearm-` or `Start-` through a non-interactive channel such as Azure VM Run Command without `-Confirm:$false`: both scripts use `ConfirmImpact=High`, wait for a prompt nobody can answer, and the hung execution blocks further Run Command calls (`Conflict: Run command extension execution is in progress`) until it is ended;
- rearm while a worker process is running (the script refuses).

**Prevent.** Before a planned reboot or patching, run `Stop-ScomWorkerTask.ps1` (cooperative stop), reboot, then start the task with `Start-ScomWorkerTask.ps1`. A clean stop followed by a reboot has not been lab-tested, and unattended recovery after an unclean reboot is not provided: after any unplanned restart, check `Get-ScomWorkerTaskStatus.ps1` and rearm as above. Consider alerting on `get_source_status` freshness so an expired read model is noticed before users ask.

*Lab evidence (sanitized):* a VM restarted without a cooperative stop was down for about six and a half hours. The startup task exited with return code 1 on each launch; the status file still said `running` with the preboot process id. One operator rearm followed by a start restored `published` publications and the agent answered again. The exact reason the worker process exited was not independently captured beyond the documented status codes.

## Receiver startup and configuration

| Code or message | Emitted by | Likely cause | Fix |
|---|---|---|---|
| `SCOM_SERVER_FAILED Code=OPERATIONAL_LOG_OR_HOST_FAILED` | `Program.cs` console | Host failed to start: invalid settings, unwritable log directory, or database refusal | Run `--validate-setup`; check the log directory exists, is on fixed NTFS and writable by the app-pool identity |
| `OPERATIONAL_LOG_IO_FAILED` | `OperationalLogging.cs` | Log sink not writable (read-only, missing, ACL) | Fix the directory and ACLs; setup creates it, runtime does not |
| "Operational log directories must be separate for server and worker." | `OperationalLogging.cs` | Receiver and worker share a directory | Use separate non-nested directories |
| "Operational log exceeds its configured byte budget." | `OperationalLogging.cs` | Log file larger than `MaxFileBytes` at start | Archive or remove the oversized file while stopped |
| "Read model database belongs to a different configured scope or lacks pinned state" | `ReadModelStore.cs` | Pinned policy (scope, allowed properties/metrics, alert descriptions, Windows hosting/caption, preview) changed | Revert, or follow [policy-change procedure](configuration-reference.md#4-policy-changes) |
| Database refusal: orphaned `-journal`/`-wal`/`-shm`, unsupported schema, over `MaxDatabaseBytes`, WAL mode | `ReadModelStore.cs` | Unclean copy/restore or smaller budget | Restore a clean database file; raise `MaxDatabaseBytes` within limits |
| `SCOM_SETUP_CONFIGURATION_INVALID ErrorType=<T>` | `--validate-setup` | A rule in [configuration-reference.md](configuration-reference.md#5-what---validate-setup-enforces) failed; `<T>` is the exception type only | Compare receiver and worker settings section by section |
| `SCOM_SETUP_SOURCE_EVIDENCE_REQUIRED` (exit 2) | `--validate-setup` | `scopeVisibilityVerified` or the membership/enumeration contract flag is not true | Complete the source review; flags are never inferred |
| `WORKER_STOP_REQUEST_REFUSED`, `WORKER_REARM_REFUSED` | `Program.cs` console | Wrong runtime-state directory, no status file, or rearm not needed | Pass the exact `--runtime-state-dir` |

| `INVALID_ARGUMENT` | Parameter outside the allowed values or limits | See parameter tables in the spec |

| `CURSOR_DATASET_CHANGED` | A new dataset was committed while paging | Restart paging |
| `NOT_FOUND` | Entity or object id not in the current dataset | Check id; the dataset may not contain it |
| `SOURCE_UNAVAILABLE` / `READ_MODEL_EXPIRED` | Oldest domain `asOfUtc` older than `UnavailableMinutes` | Check the worker (`Get-ScomWorkerTaskStatus.ps1`), then network and publisher codes. If the host was just restarted, see [After a server restart](#after-a-server-restart-agent-says-read_model_expired) |
| `SOURCE_UNAVAILABLE` / `READ_MODEL_LATEST_COLLECTION_UNAVAILABLE` | No committed dataset, or a new ingestion session began and has not committed | Wait for commit; check worker logs |

| `SOURCE_UNAVAILABLE` / `WINDOWS_PROJECTION_MISSING` | Dataset has no Windows projection (worker not `supportedWindows`) | Check `inventoryKind` and `windowsMapping` |
| `SOURCE_UNAVAILABLE` / `NO_USABLE_OBSERVATIONS_FOR_REQUESTED_METRIC_WINDOW` | No samples for the metric in the window | Check metric collection; try a larger window |
| `SOURCE_UNAVAILABLE` / `REQUEST_COULD_NOT_BE_COMPLETED`, HTTP 500 `REQUEST_FAILED` | Unexpected server error | Capture the receiver log entry (`RequestFailed`, `ToolFailed`) and open an issue |
| `SOURCE_UNAVAILABLE` / legacy snapshot reasons (`LEGACY_SNAPSHOT_DISABLED`, `LATEST_COLLECTION_FAILED_OR_MISSING`, `COLLECTION_CHANGED_DURING_READ`, `SNAPSHOT_OR_STATUS_INVALID_OR_UNREADABLE`, `SOURCE_SIZE_LIMIT`, `INVALID_SNAPSHOT_JSON`, `DUPLICATE_JSON_PROPERTY`, `SNAPSHOT_SCHEMA_SCOPE_OR_STATUS_INVALID`, `COLLECTOR_STATUS_MISMATCH`, `SOURCE_EXPIRED_OR_INVALID_TIME`, `SOURCE_COLLECTIONS_INVALID`, `DEVICE_INVALID_OR_OUTSIDE_SCOPE`, `AMBIGUOUS_DEVICE_IDENTITY`, `AMBIGUOUS_OR_UNEXPECTED_DEVICE_COVERAGE`, `VOLUME_INVALID_OR_OUTSIDE_SCOPE`, `AMBIGUOUS_VOLUME_PARENT`, `SAMPLE_INVALID_OR_OUTSIDE_SCOPE`, `MEMORY_SAMPLE_EXCEEDS_TOTAL`, `CONFLICTING_SAMPLE_DUPLICATES`) | Only with `Source.SnapshotEnabled`; the snapshot files are missing, stale, oversized or fail validation | Not used by the supported indexed configuration (`SnapshotEnabled=false`); otherwise re-run the snapshot collector and compare with `Source` settings |
| `LIVE_NOT_ENABLED`, `LIVE_PROVIDER_UNAVAILABLE`, `LIVE_RATE_LIMITED`, `LIVE_QUEUE_FULL`, `LIVE_TIMEOUT`, `LIVE_PROVIDER_UNVERIFIED`, `LIVE_PUBLISHER_FORBIDDEN`, `LIVE_RESULT_INVALID`, `LIVE_REQUEST_EXPIRED_OR_UNKNOWN`, `LIVE_RESULT_BUDGET`, `LIVE_REPLAY_CONFLICT`, `LIVE_DATASET_CHANGED`, `LIVE_SOURCE_UNAVAILABLE`, `LIVE_PROTOCOL_INVALID` | Targeted live is disabled (default) or its provider, limits or policy hash are not satisfied | See [targeted-live-verification.md](targeted-live-verification.md); live checks are disabled in the supported setup |
| HTTP 429 on `/mcp` (no JSON body) | The caller exceeded 30 requests per minute or 4 concurrent requests (policy `ScomRead`, per `oid`) | Retry after the window; have the agent page with fewer, larger requests and avoid parallel tool calls |
| `SOURCE_UNAVAILABLE` / `SOURCE_BRIDGE_EXECUTABLE_PATH_REQUIRED` | The collector start path was relative or missing (the PATH search was removed) | Use the absolute `powershell.exe` path from setup; do not edit it by hand |

## Ingestion rejections (receiver, HTTP 409 `INGESTION_REJECTED`)

Emitted by `ReadModelStore.cs`; surfaced to the worker as `PUBLISHER_<reason>` or `PUBLISHER_HTTP_409`.

| Reason | Likely cause | Fix |
|---|---|---|
| `PUBLISHER_FORBIDDEN` | Token `oid`, role or app-only requirement not met | Add the publisher's enterprise-app object id to `ReadModel.PublisherObjectIds`; assign app role `Scom.Ingest`; token must have no `scp` |
| `COLLECTION_ALREADY_IN_PROGRESS` | Another unexpired staging session exists | Wait for `SessionMinutes` (default 30) to expire or for the other run to finish; check for two workers |
| `SESSION_EXPIRED_EMPTY_RESERVATION` | Reservation expired before any batch | The worker may replace its reservation once per attempt when the checkpoint has no pending payload; both sides need the same package version |
| `SESSION_REPLAY_OR_EXPIRED`, `SESSION_INVALID`, `SESSION_INVALID_OR_EXPIRED`, `SESSION_ALREADY_CONSUMED` | Session id reused, expired or unknown | Let the worker start a new attempt; if repeated, check clocks and `SessionMinutes` |
| `SESSION_LEDGER_LIMIT` | 1,000,000 sessions used | Policy-change procedure to a new database ([configuration-reference.md](configuration-reference.md#4-policy-changes)) |
| `BATCH_SEQUENCE_INVALID`, `BATCH_REPLAY_CONFLICT`, `COMMIT_REPLAY_CONFLICT` | Gap, reorder or changed body on replay | Internal consistency check; capture the operational log and open an issue |
| `BATCH_LIMIT`, `MANIFEST_SIZE_LIMIT`, `DATASET_SIZE_LIMIT`, `RECORD_COUNT_LIMIT` | A configured size/record budget is exceeded (HTTP 413 for transport-level overruns) | Narrow the scope or raise limits within the ranges in [configuration-reference.md](configuration-reference.md) on both sides; see [sizing-and-scope.md](sizing-and-scope.md) |
| `BATCH_ARRAYS_INVALID`, `JSON_INVALID`, `WINDOWS_BATCH_INVALID_OR_DISABLED` | Malformed body; Windows batch sent while `WindowsToolsEnabled=false` | Match worker `inventoryKind`/`windowsMapping` with receiver `WindowsToolsEnabled` |
| `SCOPE_UNVERIFIED_OR_MISMATCH`, `MEMBERSHIP_INVALID`, `MEMBERSHIP_DUPLICATE`, `OBJECT_MEMBERSHIP_INVALID`, `RELATIONSHIP_OUTSIDE_SCOPE` | Worker scope differs from receiver pin, or data outside the approved scope | Align `ManagementGroupId`, `ScopeKind`, `GroupId` |
| `PROPERTY_NOT_APPROVED_OR_OVERSIZED` | Property not in `AllowedPropertiesByClass` for the class, or value over 2000 characters | Align allowed properties on both sides (a policy change) |
| `METRIC_INVALID_OR_DUPLICATE`, `WINDOWS_METRIC_UNIT_INVALID` | Metric unit/range/time invalid or duplicate | Internal consistency check; capture the operational log and open an issue |
| `SOURCE_TIME_REGRESSION`, `TIME_INVALID`, `COVERAGE_MISSING`, `COVERAGE_INVALID`, `ALERT_HISTORY_INVALID`, `OBJECT_INVALID`, `ALERT_INVALID`, `RECORD_DUPLICATE`, `TEXT_INVALID`, `ID_INVALID` | Manifest or record validation failed (a time older than the previous dataset, missing domain coverage, invalid text or id) | Check worker and receiver clocks; otherwise internal consistency check; capture the operational log and open an issue |
| `WINDOWS_PROJECTION_DISABLED`, `EXPECTED_COMPUTER_MEMBERSHIP_REQUIRED`, `EXPECTED_COMPUTER_MEMBERSHIP_INVALID`, `WINDOWS_DEVICE_OUTSIDE_SCOPE_OR_HEALTH_MISMATCH`, `WINDOWS_VOLUME_OUTSIDE_SCOPE`, `WINDOWS_COMPLETE_INVENTORY_MISMATCH`, `WINDOWS_DOMAINS_EXPIRED` | Windows projection disagrees with receiver settings or manifest | Align `WindowsToolsEnabled` and the Windows mapping on both sides |
| `WINDOWS_METRIC_HOSTING_INVALID`, `WINDOWS_METRIC_HOSTING_AMBIGUOUS`, `WINDOWS_OS_CAPTION_PROPERTY_NOT_APPROVED`, `WINDOWS_OS_CAPTION_SOURCE_MISMATCH` | `WindowsMetricHosting` or `WindowsOsCaptionProperty` differs from the worker `windowsMapping` | Align per [configuration-reference.md](configuration-reference.md#3-settings-that-must-match-between-receiver-and-worker) |
| `OFFLINE_HOSTING_PREVIEW_ALREADY_CAPTURED`, `OFFLINE_HOSTING_PREVIEW_MUST_REPORT_UNVERIFIED_COVERAGE`, `OFFLINE_HOSTING_PREVIEW_POLICY_REQUIRED`, `OFFLINE_HOSTING_PREVIEW_MONITORING_ROLE_UNVERIFIED` | Hosting lab preview preconditions not met or preview already captured | Lab-only feature; not acceptance evidence. Use a new database and checkpoint |
| HTTP 429 | Another ingestion request was in flight (concurrency limit 1) | Ensure a single worker; retries are automatic |
| HTTP 408 | Body not received within `RequestBodyTimeoutSeconds` | Check network path and proxies |

Receiver event `IngestionAccepted` / `SCOM_INGESTION_ACCEPTED` means a request was accepted. `IngestionRejected` carries the reason only for `SESSION_EXPIRED_EMPTY_RESERVATION`, `SESSION_REPLAY_OR_EXPIRED`, `COLLECTION_ALREADY_IN_PROGRESS`, `SESSION_ALREADY_CONSUMED`, `SESSION_LEDGER_LIMIT` and `SESSION_INVALID`.

## Worker, scheduler and runtime state

| Code | Emitted by | Likely cause | Fix |
|---|---|---|---|
| `WORKER_CONFIGURATION_OR_EXECUTION_FAILED` (`SCOM_WORKER_FAILED`) | `Program.cs` | Configuration invalid, or an unclassified execution failure | Run `--validate-setup`; read `worker.log` |
| `WORKER_CONFIGURATION_JSON_INVALID` | `CollectionWorkerHost.cs` | `worker.json` invalid, duplicate properties, over 1 MB, or relative path | Fix JSON; use an absolute path |
